# v0.2.0 — what the first deployment found, and lifecycle management

A small release on top of [v0.1.0](v0.1.0.md), and an honest one: most of it is
fixing things that only broke once the system ran somewhere other than a laptop.
The rest closes two gaps where the backend already held a value the interface
never showed.

No database migration. No schema change to `service.yaml`. Upgrading is a pull
and a restart — see [Upgrading](#upgrading-from-v010).

**Running at <https://opsatlas.hoseacodes.com>.**

---

## Fixed — three faults the first real deployment found

None of these could have been caught on a laptop, which is the argument for
deploying rather than describing a deployment.

**The documented first start was impossible.** The production compose file derived
`OPSATLAS_BOOTSTRAP_ISSUER` from `OPSATLAS_ISSUER_ID` unconditionally, while the
runbook says to leave the subject empty until the issuer has assigned one. The
control plane refuses to start on half an identity — correctly, because an issuer
with no subject provisions nobody. It now derives the issuer only when a subject
exists.

**The console image was permanently unhealthy while serving traffic perfectly.**
Its healthcheck asked for `localhost`; the container's `/etc/hosts` maps that to
both `127.0.0.1` and `::1`, and Next's standalone server binds `0.0.0.0` — IPv4
only. `wget` tried `::1` and got refused. It passed locally, where the resolver
ordered the two the other way. Now explicit: `127.0.0.1`. The control plane is
unaffected, and was checked rather than assumed — Tomcat listens dual-stack.

**`publish.yml` produced a `latest` tag**, which `deploy/production/README.md` and
[ADR 0014](../adr/0014-deployment-is-one-box.md) both claimed it never did.
`docker/metadata-action` adds one on a semver tag unless told otherwise;
`flavor: latest=false` makes the claim true. **The `latest` tags already published
for `0.1.0` still exist and should be deleted from GHCR** — they are not covered
by this fix, which only stops new ones.

**The console announced the wrong environment.** The shell read the hardcoded
string `local`, so the production deployment spent its first day telling everyone
it was a laptop. It is now `OPSATLAS_ENVIRONMENT`, read at request time so one
image still runs against any deployment. A `NEXT_PUBLIC_` variable would have
baked it in at build and made the image environment-specific, which is the
property the Dockerfile went out of its way to preserve.

## Added — a service can be retired or deleted

`PUT` existed with no interface, and `DELETE` did not exist at all. Both are now
reachable from the service detail page's Manage section, each sending `If-Match`
built from the version that page was rendered with.

**Retiring is the recommended path.** `spec.lifecycle: retired` through the edit
form keeps the entry, its scorecards and its probe history. That is what a catalog
is for. Deletion is for a registration that should not exist.

`DELETE /api/v1/services/{slug}`:

- **`If-Match` is required**, as it is on update. Deleting something that has
  changed since it was read is the one mistake in this API that cannot be undone
  from inside the system, so a delete with no stated version is refused with 428
  rather than applied.
- Answers **204**, declared rather than returned through a `ResponseEntity`, so
  the generated contract says 204. Springdoc infers 200 from `ResponseEntity<Void>`,
  which would have been the contract stating something the endpoint does not do.
- **The audit entry survives the row it describes.** `audit_event` declares no
  foreign key to `service`, so "what happened to orders-api" stays answerable
  after orders-api is gone.

The hard delete is safe because of the schema, not because of care: `environment`,
`policy_result` and the observation tables cascade, and `source.service_id` is set
null so a watched repository stays watched. Deleting a service that a source still
watches is therefore temporary — the next sync registers it again.

The operation is in the OpenAPI document and the generated TypeScript client.
`OrgIsolationIT` covers it across the organization boundary, with a positive
control so the leak check cannot pass against an endpoint that answers nobody.

## Added — a declared dashboard is now a followable link

`spec.observability.dashboard` was validated, parsed and dropped. No column, no
rule, nothing shown — declaring one did nothing. `ServiceDetail` already carried
the whole validated manifest, so this was rendering rather than plumbing.

The link is scheme-checked in the console as well as in the schema. A manifest is
another repository's document and an `href` is a small execution of it, so a link
renders only if it parses as an absolute URL whose protocol is `https:`.
`manifestLinks.test.ts` refuses `javascript:`, `data:`, `http:` and
protocol-relative URLs; a relative path is refused too, since it would resolve
against the console's own origin and let a manifest link into this app.

The console cannot vouch for where the link *goes*. A dashboard URL is the
declaring team's claim about their own dashboard, and it is presented as that.

`spec.observability.serviceName` — the name telemetry arrives under — is shown on
the same panel, for the same reason: it was already stored and never displayed.

## Upgrading from v0.1.0

```bash
# on the host
git pull
export OPSATLAS_TAG=0.2.0
docker compose -f deploy/production/docker-compose.yml pull
docker compose -f deploy/production/docker-compose.yml up -d
```

Two things to know:

1. **Remove the temporary console healthcheck override** if you added one to work
   around the `::1` fault in `0.1.0`. A `git pull` wipes it anyway, which is also
   when the fixed image arrives. Leaving it on a tag later than `0.1.0` is
   harmless but pointless.
2. **Set `OPSATLAS_ENVIRONMENT`** if the shell should say anything other than
   `production`. The production compose file defaults it to `production`; an
   unconfigured console still says `local`.

No migration runs. Flyway has nothing new to apply.

## Unchanged, and still true

Everything in [v0.1.0's "what this release deliberately does not do"](v0.1.0.md#what-this-release-deliberately-does-not-do)
still applies. The ones most worth repeating:

- **No backups, no zero-downtime deploy, no redundancy.** `docker compose up -d`
  stops and starts containers. Do not assume the data survives the box, and do not
  call this highly available.
- **Nothing has been load-tested or security-tested.** No performance, scale,
  availability or security claim is made anywhere, because none has been measured.
- **Health is probe availability, not an SLO.**
- **The scorecard scores manifests, not running systems.**
- **It is not multi-tenant.** The data model is single-tenant, shaped so that
  multi-tenancy is possible later.
- **The SSH hardening on the deployment host was never applied.**

Still outstanding from `v0.1.0`: the `latest` tags published for `0.1.0` want
deleting from GHCR.
